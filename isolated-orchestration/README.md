# REA Stealth — Isolated Orchestration

Local-first, provider-independent task orchestration. Built as an optional module on top of the REA Stealth repository, without changing its existing reverse-engineering tools.

## Architecture

- One MCP server implementation, with `--role master` or `--role worker --task ID` startup profiles.
- Master: creates and reviews individual task projects, reads the task graph, checks readiness.
- Worker: receives only its assigned instructions, obtains an exclusive renewable lease, requests dependencies, and can submit a result or report a blocker.
- Local filesystem stores plans, worker project files, and result manifests; no paid model API is needed.
- Worker roles have separate advertised MCP tools; master methods are not callable through worker connections.

See [desktop setup](docs/desktop-setup.md) for stdio configuration examples.

## CLI workflow

From this directory:

```sh
node src/cli.mjs init ./demo
node src/cli.mjs add ./demo ./example-task.json
node src/cli.mjs ready ./demo
node src/cli.mjs submit ./demo parser "Implemented"
node src/cli.mjs review ./demo parser accept "Tests passed"
npm test
```

Task specification example:

```json
{"id":"parser","title":"Parser","instructions":"Build a parser for the provided fixtures.","acceptance":["Pass parser tests"],"dependencies":[]}
```

MCP launch examples:

```sh
node src/mcp.mjs --role master --workspace C:/REA-workspace/project
node src/mcp.mjs --role worker --workspace C:/REA-workspace/project --task parser
```

## Status and caveats

This is an **initial optional module**, not yet wired into the main `rea` CLI's existing command router or REA MCP catalog. It exposes a standalone MCP stdio endpoint in the same repository.

Role isolation is only enforced in this module's MCP interface and bridge-mediated file functions. It **does not prevent unrestricted file/shell tools in a desktop application from reading accessible Windows folders**. NTFS-enforced identity separation is deferred as requested. A local user capable of editing MCP launcher configuration can start the master profile.

A filesystem watcher and serialized registry updates are available, but no automatic ChatGPT desktop wake-up or GUI automation is implemented. The worker lease and lock-recovery logic require runtime validation on Windows and Linux. Desktop compatibility must be verified for each actual client before activation.

Existing reverse-engineering tools and upstream build behavior remain untouched.

## Local completion notifications

Run `node src/watch.mjs C:/REA-workspace/project` in a persistent local terminal. It outputs JSON lines for submissions and scans existing submission records on startup. It is an optional observer: it does not automatically launch or resume AI desktop applications, and must not be treated as a security boundary. A later integration will connect these events to the desktop coordinator.

## New master workflow

`init` generates `control/master-mcp.json` and each task generates its own `.mcp.json` and minimal Claude Code configuration. Worker `get_task` claims a renewable lease; a second session targeting the same task cannot claim it while the lease is live. Master can call `recover_expired` after crashes. Master tools `pending_events` and `acknowledge_event` expose durable submission events.

Workers can request dependencies. The orchestrator approves them and may use `provision_text_resource` to stage a UTF-8 resource in `resources/`; arbitrary package installation is not implemented. The orchestrator can call `inspect_deliverables` and, after acceptance, `import_deliverables` to copy worker outputs into an isolated integration staging area. This does not run arbitrary worker code, merge into the master repository, or validate application behavior.

CI source: [isolated orchestration tests](../.github/workflows/isolated-orchestration-tests.yml). Tests are committed but no passing Actions run has been verified from this environment.

## Local operations and debugging

From `isolated-orchestration` on Node 22+:

```powershell
npm test
node src/cli.mjs list C:/REA/test-project
node src/cli.mjs events C:/REA/test-project
node src/cli.mjs requests C:/REA/test-project
node src/cli.mjs inspect C:/REA/test-project parser
node src/cli.mjs recover C:/REA/test-project
```

The CLI also supports `resolve-request ROOT REQUEST_ID approved "Reason"`,
`provision-text ROOT REQUEST_ID filename local-file.txt`,
`import ROOT TASK_ID`, `ack-event ROOT EVENT_ID`, and explicit
`claim/renew/release ROOT TASK_ID OWNER_ID`. Never use `import` before
reviewing and accepting a task.

Claude Code project folders are generated by `create_task` or `add`.
Each new task includes a project-scoped worker MCP file; start Claude Code from
the specific worker folder and verify the `rea-worker` connection via `/mcp`.
The local master connection is described by `control/master-mcp.json`.
Project-scoped MCP configuration does *not* prevent access to readable files
outside the worker directory. Do not use this for secret isolation.

**Limitations:** This standalone module does not yet automatically launch,
resume or notify ChatGPT/Claude Code sessions. New source files are covered by
CI tests, but a successful CI run has not yet been confirmed.

## Launch multiple Claude Code workers (opt-in)

On Windows, first install and sign in to Claude Code from a normal terminal.
The launcher opens **separate interactive Claude Code terminal windows** for up
to four ready tasks, each with its own working directory and project-scoped MCP
configuration. It does not send a prompt automatically, bypass permission
prompts, or grant filesystem/network isolation.

Preview without launching:

```powershell
node src/cli.mjs launch-ready C:/Users/levmi/REA-test-project
```

Launch up to two ready workers:

```powershell
node src/cli.mjs launch-ready C:/Users/levmi/REA-test-project --max=2 --execute
```

In each new Claude Code terminal, verify its project MCP with `/mcp` and ask:
"Use rea-worker get_task to claim this project, complete TASK.md and submit
your work." Each process gets an exclusive lease after calling `get_task`.
Use `renew_lease` periodically for long interactive sessions; the default
lease expires after two minutes, and no automatic heartbeat exists yet.

Master MCP tools: `plan_worker_launch` previews eligible sessions, and
`launch_ready_workers` requires `{ "confirm": true }` to open them.
**Repeated launch commands can create duplicate windows**; each task's MCP
lease, not the launcher, enforces exclusive task ownership.

On Linux, the launcher currently requires `x-terminal-emulator`; macOS is
not yet supported. A Claude Code subscription or user-provided model
authentication is still required for real model execution. These terminal
launches do not require REA Stealth to collect or store provider credentials.
